# Производительность

Тёплый вызов `.get()` читает `Map.get(key)` и при необходимости напрямую вызывает `new Ctor(...)`. Сценарии бенчмарка охватывают следующие решения в runtime:

| Решение | Эффект |
| --- | --- |
| Явные регистрации | Сборка контейнера делает плоский `Map.set` на сервис. Нет побочных эффектов декораторов, парсеров имён конструкторов и таблиц метаданных. |
| Закешированные singleton- и scoped-сервисы | Тёплый вызов `.get()` читает `cache.get(key)` до проверок циклов и времени жизни. Запасной `cache.has(key)` нужен только для явно зарегистрированного `undefined`. |
| Прямые вызовы конструкторов | Классы с 0-7 зависимостями идут по прямому пути `new Ctor(...)`. Конструкторы с большим числом аргументов используют `Reflect.construct`. |
| Асинхронные фабрики | Фабричный `Promise` кешируется как есть, поэтому параллельные вызовы делят одну начатую инициализацию, а `.get()` остаётся синхронным. |
| Runtime-контракт | Default/`fast: false` сохраняет runtime-проверки и точную mutable parent chain. `fast: true` отключает проверки и включает fixed-topology lookup scope. |

## Набор бенчмарков

Сравнительный набор измеряет `InferDI (fast)` и `InferDI (default)` вместе с InversifyJS v8, Awilix v13 в режимах PROXY и CLASSIC, TSyringe v4, TypeDI v0.10 и Typed Inject v5. В исходном результате записаны версии пакетов и параметры машины, на которой выполнен прогон.

**Проверка корректности перед замерами**

До запуска Tinybench каждый адаптер проходит contract suite. Все адаптеры должны предоставить одинаковый наблюдаемый граф:

- `Logger`, `Config`, `Repo` и `Service` работают как корневые singleton-сервисы
- transient-узлы графа создают новые экземпляры
- каждый scope кеширует собственный `ScopedService` и использует общий корневой logger
- lazy-доступ откладывает resolve целевого сервиса
- каждый заявленный teardown API вызывает disposer scoped-сервиса

Эти проверки не позволяют различиям в lifetime или identity попасть в сравнение времени. Сценарии измеряют стоимость операций после успешной проверки адаптера.

**Методика измерений**

Публичный runner устанавливает зависимости с frozen lockfile, проверяет типы benchmark workspace, собирает production ESM artifact InferDI и запускает contract suite против этой сборки. Затем он измеряет участников с такими условиями:

1. Один сбалансированный Latin-square блок содержит восемь раундов по числу участников.
2. Каждый участник один раз занимает каждую позицию запуска и один раз следует за каждым другим участником. `InferDI (fast)` запускается раньше `InferDI (default)` в четырёх раундах и позже в остальных четырёх.
3. Каждый участник работает в отдельном новом Node-процессе, поэтому реализации не делят JIT feedback, inline caches и историю GC.
4. Tinybench прогревает каждый сценарий 50 ms и измеряет его 100 ms. Один sample выполняет batch подходящего для операции размера.
5. Для каждой комбинации участника, сценария и раунда runner делит медианную длительность batch на его размер и записывает нормализованное значение `ns/op`.
6. Reporter агрегирует восемь значений по раундам с помощью медианы и median absolute deviation (MAD).

Меньшее значение `ns/op` означает более быструю операцию. MAD показывает разброс вокруг медианы, но не является доверительным интервалом. Изоляция процессов и сбалансированный порядок уменьшают смещение, однако не исключают влияние планировщика ОС, частоты CPU, решений JIT и момента запуска GC.

**Границы сценариев**

Каждый сценарий изолирует одну часть работы контейнера. Production-код сочетает несколько этапов в зависимости от используемых lifetime.

| Группа нагрузки | Сценарии | Какая работа контейнера представлена |
|---|---|---|
| Тёплый доступ | Hot singleton resolve, warm scoped resolve, lazy resolve | Чтение закешированного сервиса или доступ через существующую lazy-обёртку |
| Создание объектов | Transient resolve, deep graph, wide graphs | Промахи кеша, обход зависимостей, подготовка аргументов и вызовы конструкторов |
| Запуск и холодный доступ | Registration, first resolve | Настройка графа и первое заполнение кешей |
| Жизненный цикл scope | Scope creation, first scoped resolve, sync teardown, async teardown | Владение scope на время запроса или задачи от создания до очистки |

Setup hooks Tinybench подготавливают холодные графы и scope за пределами измеряемой области. Очистка в сценариях регистрации и resolve также выполняется вне замера. Teardown-сценарии, напротив, измеряют саму очистку.

TypeDI получает `N/A` в Registration, потому что сравнимые определения сервисов выполняются как побочные эффекты декораторов при загрузке модуля, а timer регистрации не включает этот этап. В teardown-строки входят библиотеки с эквивалентным публичным контрактом: InversifyJS получает `N/A`, TypeDI участвует в sync teardown, а Awilix, TSyringe и Typed Inject участвуют в async teardown. InferDI предоставляет оба контракта очистки.

**Интерпретация результата**

Один из режимов InferDI показывает минимальную медиану или делит первое место в 12 из 13 сценариев. `InferDI (fast)` показывает такой результат в 11 сценариях. Наиболее заметные преимущества относятся к регистрации, первому resolve, созданию transient- и других графов, созданию scope и первому scoped resolve. Эти операции проходят через участки, где на замер влияют плоский registry InferDI, прямые вызовы конструкторов и короткий путь после промаха кеша.

`Warm scoped resolve` — единственный сценарий, где ни один режим InferDI не показывает минимальную медиану. Typed Inject показывает 7.975 ns, InferDI default — 8.250 ns, а InferDI fast — 8.387 ns. Эта строка измеряет одно чтение уже закешированного значения из существующего scope. Она не включает создание scope, первый scoped cache miss и teardown, которые тот же production-запрос может оплачивать отдельно.

**Почему `fast` не показывает меньшее время в каждой строке**

`fast: true` меняет защищённые cache misses, создание объектов, инвалидацию при регистрации и поиск по родителям в scope с фиксированным деревом. После прогрева некоторые сценарии не выполняют эти ветки:

- Hot singleton resolve возвращает значение из `cache.get(key)` до чтения флага `fast`. Оба режима показывают медиану 6.233 ns.
- Warm scoped resolve использует тот же возврат из кеша. Fast показывает 8.387 ns, а default — 8.250 ns: разница 0.137 ns получена на одном и том же пути реализации. Она сопоставима с указанными значениями MAD.
- Sync teardown использует одну реализацию disposal в обоих режимах. Разница медиан 1.370 ns равна MAD результата fast в этом прогоне.
- В async teardown и lazy resolve fast показывает небольшой выигрыш, хотя их steady-state работа тоже не получает прямой пользы от отключённых guards. К таким небольшим различиям следует относиться так же осторожно.

В независимых Node-процессах одинаковые пути могут получить разный JIT-код или столкнуться с разным таймингом scheduler и GC. Latin-square порядок и медиана восьми раундов уменьшают эти эффекты, но не устраняют их. Небольшие перестановки в warm scoped resolve и sync teardown не доказывают регрессию fast-режима. Повторные прогоны на контролируемой машине дают более надёжные данные для различий меньше одной наносекунды или в несколько процентов.

Крупные различия между fast и default возникают там, где реализация меняется. Медиана default в 1.29× выше для десятиуровневого transient-графа, в 1.22× для first resolve, в 1.20× для wide graph с четырьмя зависимостями и в 1.12× для first scoped resolve. Такое направление соответствует отключённому учёту циклов и lifetime, а также fixed-topology lookup в scope.

**Сопоставляйте сценарий с приложением**

Reporter не рассчитывает общий score, потому что приложения используют разные сочетания операций контейнера. Долгоживущий процесс может один раз зарегистрировать граф и большую часть времени читать тёплые singleton. HTTP-адаптер может для каждого запроса создать scope, один раз разрешить scoped-граф, читать закешированные scoped-значения и затем закрыть scope. Worker может создавать transient-графы без scope.

Не усредняйте относительные коэффициенты разных строк. Сценарии используют разные batch sizes и независимые timing regions. Выберите строки, соответствующие измеренному паттерну resolve в приложении, а затем профилируйте приложение целиком вместе с framework и I/O.

Сравнение относится к записанным версиям пакетов, адаптерам, fixtures и машине. Каждая библиотека сохраняет собственную публичную модель lifecycle, поэтому `N/A` означает отсутствие эквивалентной операции для этой строки. Бенчмарк измеряет overhead контейнера, а не полную задержку запроса.

## `fast: true`

`new Container({ fast: true })` убирает runtime-учёт циклов, отслеживание singleton-стека и `try`/`finally` вокруг защищённого пути resolve. Фиксированные scope читают registry owner напрямую, не проходя цепочку родителей, а delegated singleton после первого resolve зеркалируется в cache scope. Default scope при каждом локальном промахе проходит точную цепочку родителей, поэтому мутации остаются видимыми. Fast-контейнеры пропускают защитную инвалидацию при регистрации. Дедупликация owned-инстансов по-прежнему выполняется во время disposal.

Default `new Container()` и явный `{fast: false}` сохраняют runtime-проверки и mutable graph.

Включайте `fast: true` только после тестов, которые прогнали граф с `fast: false`. TypeScript не видит singleton-циклы, transient-циклы, динамические ключи, `as`-касты и фабрики, захватившие внешний контейнер с более широким типом. Регистрируйте каждый runtime-ключ один раз в одной линейной fluent-цепочке, завершите регистрацию до первого resolve или создания scope, не меняйте активированное дерево и закрывайте дочерние scope раньше предков.

После такой проверки `{fast: true}` может уменьшить стоимость регистрации, промахов кеша, создания графов и lookup в fixed scope. Тёплые cache hits и disposal используют общие пути, поэтому перед выбором runtime-контракта измерьте этапы, которые преобладают в приложении. Оставляйте `fast: false` для разработки, тестов, hot reload и любого дерева, которое меняется после активации.

## Детали горячего пути

### Создание transient-сервисов

`registerClass` остаётся основным вариантом для transient-сервисов. Меняйте его только после профилирования графа, который часто получает много разных transient-классов с одинаковым числом зависимостей.

В таком узком V8-hotspot явная фабрика создаёт отдельное место вызова для каждого сервиса:

```ts
const container = new Container()
  .declareScopeInputs<{ context: RequestContext }>()
  .registerClass('schema', Schema, [])
  .registerFactory(
    'parseRequest',
    (c) => new ParseRequest(c.get('context'), c.get('schema')),
    ['context', 'schema'],
    'transient'
  )
```

Фабрика повторяет список зависимостей, поэтому используйте её только при измеримом выигрыше. Общий generic helper уберёт отдельное место вызова и сведёт оптимизацию на нет.

### Представление ключей

Symbol-ключи могут помочь в плотных циклах resolve, потому что `Map` сравнивает их по идентичности. Строковым ключам нужен хеш, а при коллизии - посимвольное сравнение. В большинстве приложений разница не измеряется, поэтому переходите на symbol-ключи только после сигнала профилировщика.

cd benchmarks
pnpm install --frozen-lockfile
pnpm run bench:quick   # локальная проверка source
pnpm run bench:public  # production artifact, новый процесс для каждого subject
