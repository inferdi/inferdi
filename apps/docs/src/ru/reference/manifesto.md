# Архитектурный манифест ядра InferDI

Этот документ задаёт правила для `@inferdi/inferdi` в `packages/inferdi`. Читайте
его перед ревью любого PR, который меняет публичный API, систему типов, путь
разрешения `get()`, форму регистрации, семантику scope или поведение teardown.

## 1. Философия и обещание

### Миссия

InferDI доказывает, что DI в TypeScript может сохранять гибкость во время
выполнения без отказа от статических гарантий. Граф зависимостей — это тип
TypeScript. Если компилятор может проверить правило, InferDI должен выразить его
в публичных сигнатурах. Runtime-проверки нужны для `as`-кастов, захваченных
внешних контейнеров, динамических ключей и других мест, где TypeScript не видит
граф.

### Ценность

Граф и есть тип. Отсутствующий ключ, неверная позиция аргумента конструктора,
повторная регистрация или утечка singleton-to-scoped должны приводить к ошибке
до запуска production-кода. Runtime-контракт InferDI тоже остаётся маленьким:
без runtime-зависимостей, декораторов, рефлексии метаданных, ловушек proxy и
фреймворковой логики в core-пакете.

Разрешение с попаданием в кеш остаётся быстрым путём из одного `Map.get()`.
Создание классов использует развёрнутые по arity прямые вызовы `new Ctor(...)`
для 0–7 зависимостей и измеренный хвостовой путь для 8+ зависимостей.

Если возможность ослабляет эти обещания, отклоните её или вынесите за пределы
core.

## 2. Необсуждаемые опоры

### 2.1 Сквозная типобезопасность

Каждая публичная сигнатура должна делать неверные состояния графа невыразимыми
там, где TypeScript способен выразить правило.

- `register*` принимает `key: K & NoKeyOverlap<K, keyof T>`, где
  `NoKeyOverlap` недистрибутивно проверяет `[K & keyof T]`. Литеральные, широкие,
  символьные и union-ключи остаются доступны, но любое пересечение отклоняет
  весь ключ-кандидат, а не молча исключает один элемент union.
- `DepsOf<AllowedDeps<T, L>, A>` проверяет кортеж `deps` по позициям параметров
  конструктора и структурной совместимости.
- `AllowedDeps<T, L>` сужает контейнер, передаваемый фабрикам. Внутри
  singleton-фабрики `c.get('scoped')` является ошибкой типов.
- Замыкающая форма `registerFactory` получает контейнер, отфильтрованный по
  lifetime. Перегрузка с зависимостями получает resolver, ограниченный
  объявленными sync-ключами; `registerAsyncFactory` получает разрешённые
  позиционные значения, а не контейнер. Не смешивайте эти контракты callback.
- `Lazy`, `AsyncLazy`, `Lifetime`, `Spec`, `AsyncSpec`, `LazySpec`,
  `AsyncLazySpec`, `ScopeInputMap`, `WithRequirements`, `DependenciesMap`,
  `SpecMap`, `ContainerOptions`, `Module`, а также `Container.ReadyKeys`,
  `Container.SyncReadyKeys`, `Container.Resolve`, `Container.ResolveUnwrapped`,
  `Container.UnwrappedValue` и `Container.Providers` — публичные контракты.
  Любое изменение их совместимости или вывода типов считается изменением API,
  даже если runtime-код не меняется.
- Обобщённые resolver-функции используют `Container.SyncReadyKeys<C>` для
  `get()` и `Container.ReadyKeys<C>` для `getAsync()`. `.has()` доказывает только
  наличие регистрации; он не подтверждает sync-режим и не удовлетворяет
  отсутствующие scope inputs.
- Новая или изменённая публичная поверхность типов требует позитивных и
  негативных тестов с `// @ts-expect-error` в `container.test-d.ts` или наборе
  type-тестов декларативного async-графа. Публичные диагностические сообщения
  для модулей или scope inputs также требуют своего compiler-diagnostic fixture,
  а сгенерированные декларации должны по-прежнему проходить `consumer-dts.ts`
  на TypeScript 5.2.

Известные ограничения TypeScript нужно документировать, а не прятать. Например,
две зависимости с одинаковым структурным типом остаются взаимозаменяемыми, пока
пользователь не введёт номинальное различие через ключи `unique symbol` или
брендированные типы значений.

### 2.2 Никаких декораторов и reflect metadata

InferDI — это обычный TypeScript с target ES2022. Не добавляйте декораторы,
`reflect-metadata`, `experimentalDecorators`, `emitDecoratorMetadata`,
TS-трансформеры или плагины транспайлера.

- Тип конструктора является источником истины для типов зависимостей.
- Явный кортеж `deps` является источником истины для порядка аргументов.
- Runtime не читает имена параметров конструктора, сгенерированные метаданные
  или поля классов.

Декораторы и метаданные превращают InferDI в другую библиотеку. Они добавляют
runtime-состояние, требования к toolchain и стоимость холодного старта, которые
core-пакет отвергает.

### 2.3 Lifetime является типом

В core есть три lifetime регистрации: `singleton`, `scoped` и `transient`.
Каждая регистрация несёт свой lifetime через `Spec<V, L>` и публичное свойство
`lifetime`.

- Singleton не должен напрямую зависеть от scoped- или transient-сервиса.
  `AllowedDeps<T, L>` обеспечивает это на этапе компиляции, а стандартный
  checked-контракт — во время выполнения для кастов и динамических регистраций.
  Любой union целевого lifetime, который может включать `'singleton'`, использует
  безопасный для singleton фильтр; короткоживущие зависимости разрешены только
  union, исключающему singleton.
- `Lazy<V>` и `AsyncLazy<V>` сохраняют lifetime цели. Singleton-потребитель может
  внедрить только managed companion, у которого всё состояние target lifetime
  равно `'singleton'`. Scoped-, transient-, смешанные lifetime и union из
  managed и unmanaged значений для singleton-потребителей запрещены.
- Runtime-флаг `Registration.lazy` должен быть `true` только у lazy companion,
  чей target lifetime равен `'singleton'`.
- Runtime-флаг `Registration.owned` равен `true` только у class/factory
  регистраций, созданное значение которых принадлежит контейнеру. Для
  `registerValue`, `.override()`, lazy companion, scope inputs и transient
  результатов он равен `false`.
- Значения `registerValue`, `.override()` и scope inputs принадлежат приложению.
  Transient-результаты принадлежат вызывающему коду. Ни одно из них не попадает
  в очередь teardown.
- `.override()` — тестовая лазейка. Он должен сохранять исходные `kind`, `lazy` и
  `async`, оставаться локальным для scope и отклонять объявленные scope inputs,
  неизвестные ключи, disposed-контейнеры и ключи из локального кеша текущего
  контейнера. Проверка кеша замечает локально закешированные singleton/scoped
  регистрации, `registerValue` и повторные overrides, но не видит transient
  resolves и принадлежащие предку значения, разрешённые через checked-потомка.
  Применяйте overrides до разрешения графа даже там, где runtime-проверка не
  может доказать момент применения.
- `dispose()` затрагивает только экземпляры, принадлежащие этому контейнеру.
  Родительские и дочерние контейнеры не очищают друг друга.

#### 2.3.1 Async-режим является состоянием типа

Декларативные async-сервисы используют тот же граф, карту регистраций, кеш,
поиск scope, правила владения и путь disposal, что и синхронные сервисы.

- `registerAsyncFactory` записывает итоговый тип значения в `AsyncSpec<V, L>`,
  а не `Promise<V>`. Его кортеж позиционных зависимостей проверяется как кортеж
  конструктора и остаётся readonly, потому что регистрация сохраняет
  классифицированные позиции.
- Singleton- и scoped-async регистрации кешируют один нативный Promise, поэтому
  конкурентные вызовы `getAsync()` присоединяются к одной инициализации. Простое
  разрешение обёртки `AsyncLazy` не должно запускать её цель.
- Класс с декларативной async-зависимостью транзитивно становится async. Его цель
  разрешается через `getAsync()`, а managed companion становится `AsyncLazy`;
  класс, выбранный union-ключом sync/async, консервативно остаётся смешанным.
- `get()` отклоняет декларативные async-ключи на уровне типов. `getAsync()`
  принимает любой готовый ключ, возвращает Promise и превращает синхронные
  ошибки resolver в rejection, не создавая отдельный registry или путь
  разрешения.
- Возвращающий Promise `registerFactory` остаётся обычной синхронной записью
  графа, значением которой является сам Promise. Не переклассифицируйте этот
  legacy-контракт в `AsyncSpec` неявно.
- `Registration.async` — добавленная в конец холодная метаинформация для
  классификации зависимостей во время регистрации. Горячий путь разрешения не
  должен её читать.

#### 2.3.2 Готовность scope является состоянием типа

Scope inputs описывают принадлежащие приложению значения, которые становятся
доступны только при открытии дочерних scopes.

- `declareScopeInputs<Inputs>()` существует только в типах и не должен менять
  runtime-контейнер.
- Объявления принимают обязательные конечные string- или symbol-ключи. Числовые
  ключи, `__proto__`, широкие index signatures, необязательные свойства, union с
  разными наборами ключей и пересечения с существующим графом отклоняются.
- `createScope(inputs)` может предоставить любое подмножество отсутствующих
  inputs. Готовность распространяется на зависимые регистрации, вложенные scopes
  наследуют уже предоставленные inputs, а разрешать можно только готовые ключи.
- Переданные значения поверхностно копируются в кеш потомка, остаются
  собственностью приложения, не могут быть перерегистрированы или overridden и
  исключаются из `Container.Providers<C>`.

#### 2.3.3 Модули являются контрактами требований

`Module<TRequirements, TProvides>` описывает переиспользуемое преобразование
графа, а не точный alias всего контейнера.

- Фактический граф может содержать дополнительные записи, но каждое требование
  должно совпадать по совместимости сервиса, точному lifetime, sync/async
  состоянию, managed-lazy режиму, идентичности scope input и готовности.
- Callback модуля видит только объявленные требования. Возвращаемый граф
  сохраняет каждую фактическую запись и добавляет объявленные результаты.
- Ключи результатов не должны пересекаться с фактическим графом. Требования
  scope inputs, уже удовлетворённые вызывающим кодом, удаляются из состояния
  возвращаемого результата.
- Обобщённые helpers вида `<T>(c: Container<T>) => ...` не могут доказать
  произвольные новые ключи относительно верхней границы `DependenciesMap`.
  Используйте inline-lambda в `.use()` или именованный
  `Module<TRequirements, TProvides>`.

### 2.4 Горячий путь разрешения остаётся маленьким

Первая операция в `get()` — локальный поиск в кеше:

```ts
const cached = this.cache.get(key)
if (cached !== undefined) return ...
```

Не добавляйте работу перед этим поиском.

- Явные значения `undefined` представлены через `UNDEFINED_MARKER`; не
  возвращайте второй вызов `cache.has(key)` на путь попадания в кеш.
- `_disposed`, поиск регистрации, поиск родителя, проверки циклов, проверки
  lifetime и изменение singleton-stack находятся после быстрого пути кеша.
- Стандартные деревья проверяют локальные регистрации перед проходом по точной
  цепочке родителей. Они не хранят снимки parent lookup, поэтому изменения
  остаются видимыми без invalidation bookkeeping и lookup-метаданных на scope.
- Вызов конструктора остаётся развёрнутым по arity для 0–7 аргументов. Путь 8+
  использует `Reflect.construct` с packed array, собранным через `push`.
- `get()` остаётся синхронным. Общие массив `resolving` и `singletonStack`
  работают только потому, что одно разрешение и каждый preflight декларативной
  async-зависимости атомарно выполняются на call stack. `getAsync()` добавляет
  Promise-границу вокруг того же resolver и никогда не меняет эти стеки из
  continuation.
- Декларативные async-регистрации используют те же `regs`, `cache`, поиск scope,
  ownership и disposal, что и sync-регистрации. `Registration.async` — холодная
  метаинформация для классификации зависимостей при регистрации; `get()` её не
  читает.
- `{fast: false}` — стандартный checked mutable contract. `{fast: true}` убирает
  проверки циклов и lifetime после быстрого пути локального кеша, читает registry
  owner напрямую и зеркалирует делегированные singletons в локальный кеш. Быстрое
  дерево — fixed-graph contract: завершите все `register*`, `.use()` и
  `.override()` до первого resolve или `createScope()` и очищайте потомков до
  предков. Режим включает только литеральное значение `true`; cast или неизвестное
  значение опции безопасно оставляет checked-контракт.
- Сохраняйте порядок горячих полей `Registration`: `{kind, lazy, fn, owned}`.
  Необязательный маркер `async` можно добавлять только после них, и он не должен
  попадать на путь разрешения.

`packages/inferdi/__tests__/container.bench.ts` не проверяется в CI. Ревьюеры
должны требовать результаты benchmark для изменений в `get()`, форме объекта
регистрации, представлении кеша, поиске scope, lazy companions или вызове
конструктора. Локальная регрессия больше 5% в релевантном сценарии блокирует
merge, если PR не содержит узкого письменного обоснования.

### 2.5 Нулевые runtime-зависимости

У `@inferdi/inferdi` нет runtime-зависимостей. Так и должно оставаться.

Опубликованный bundle должен оставаться строго меньше 3 KiB (3072 байта) после
gzip. CI обеспечивает этот бюджет через `pnpm run test:bundle-size`; ревьюерам
всё равно следует проверять изменение размера в PR, которые добавляют код в
core-реализацию или публичные helpers.

### 2.6 Disposal обеспечивает соблюдение владения

Disposal закрывает только принадлежащие текущему контейнеру и закешированные
значения. Он идемпотентен, безопасен при повторном входе и независим для
родителей и потомков.

- Пометьте контейнер как disposed, сделайте snapshot и de-duplication `owned`,
  затем очистите `owned`, `cache`, `regs`, `scopeInputs` и `parent` до вызова
  пользовательских disposers. Повторное разрешение должно сразу видеть уже
  разобранный контейнер.
- Сохраняйте LIFO-порядок первого создания. Дублирующиеся записи кеша и разные
  async-фабрики, разрешившиеся в один ресурс, должны закрыть его один раз.
- Async `dispose()` совместно использует один in-flight Promise завершения,
  разворачивает закешированные Promise async-фабрик, проверяет
  `Symbol.asyncDispose` → `Symbol.dispose` → `.dispose()`, продолжает работу
  после ошибок и выбрасывает одну ошибку либо `AggregateError` для нескольких.
- Sync `[Symbol.dispose]()` вызывает только синхронные протоколы. Закешированный
  Promise или обычный `.dispose()`, возвращающий Promise, считается ошибочным
  использованием; не запускайте невидимую фоновую очистку, чтобы скрыть ошибку.
- `registerValue`, `.override()`, scope inputs, lazy wrappers и transient-значения
  остаются вне teardown контейнера, потому что владение ими не передавалось.

## 3. Фильтр PR

Для каждого PR, который затрагивает `packages/inferdi/src`,
`packages/inferdi/package.json`, `packages/inferdi/jsr.json` или core-тесты,
ответьте при ревью на следующие вопросы:

1. Сохраняет ли изменение compile-time гарантии графа или переносит правило в
   runtime-проверки без документированного ограничения TypeScript?
2. Затрагивает ли оно поведение cache hit в `get()`, форму объекта регистрации,
   поиск scope, lazy resolution или вызов конструктора? Если да, где benchmark
   evidence?
3. Добавляет ли оно runtime-зависимость, поддержку декораторов, рефлексию
   метаданных, resolve через proxy или требование к транспайлеру в core-пакет?

Отклоняйте PR, если пункт 1 переносит правило типов в runtime без причины, пункт
2 не содержит benchmark evidence или пункт 3 получает ответ «да».

## 4. Чек-лист строгого контроля

Любое изменение, соответствующее пункту ниже, требует явного обоснования в PR.

### Горячий путь и runtime-форма

- [ ] В `get()` добавлена работа перед `cache.get(key)`?
- [ ] Изменены `UNDEFINED_MARKER`, `cache`, `regs`, поиск родителя или форма
      `Registration`?
- [ ] Порядок горячих свойств `Registration` изменён с
      `{kind, lazy, fn, owned}` или необязательный маркер `async` перемещён перед
      ними?
- [ ] В checked-контракте поиск локальной регистрации перемещён после поиска
      родителя?
- [ ] В resolve добавлены `Proxy`, `Reflect.get`, `Object.defineProperty` или
      чтение метаданных?
- [ ] `get()` стал `async`?
- [ ] `get()` начал читать `Registration.async` или вычислять готовность?
- [ ] Удалены или изменены развёрнутые по arity ветки для 0–7 аргументов
      конструктора?
- [ ] Fast-scopes перестали читать registry owner напрямую или зеркалировать
      только делегированные singletons?

### Система типов

- [ ] Проверка повторных ключей ослаблена за пределами `.override()`?
- [ ] В публичном ограничении ключа `string | symbol` сужено до `string`?
- [ ] Ослаблены `AllowedDeps`, `LazySpec`, `AsyncLazySpec`, async propagation,
      readiness или фильтрация lifetime?
- [ ] Изменены `NoKeyOverlap`, `ScopeInputMap`, `WithRequirements`, совместимость
      модулей, `SpecMap` или namespace helper types?
- [ ] Объявления scope inputs принимают необязательные, числовые, широкие,
      вариантные или пересекающиеся ключи либо разрешаются до предоставления?
- [ ] Именованный модуль может скрыть отсутствующие/несовместимые требования или
      пересечь свои outputs с фактическим графом?
- [ ] В `src/` добавлены новые небезопасные `any`, `unknown as` или
      `// @ts-ignore`?
- [ ] Публичное поведение типов изменено без позитивных/негативных type-тестов,
      диагностических fixtures, где они применимы, и проверки потребителя
      деклараций?

### Зависимости и сборка

- [ ] В `packages/inferdi/package.json` добавлена runtime-зависимость?
- [ ] Добавлена peer dependency на `reflect-metadata`, `tslib` или framework
      glue?
- [ ] Превышен строгий gzip-бюджет `< 3 KiB` или ослаблена его CI-проверка?
- [ ] Потребовался TS plugin, transformer, флаг декораторов или metadata emit?

### Жизненный цикл и disposal

- [ ] `dispose()` или `[Symbol.dispose]()` перестал устанавливать `_disposed` до
      вызова disposers?
- [ ] Очистка `owned`, `cache`, `regs`, `scopeInputs` или `parent` перемещена
      после вызова disposer?
- [ ] Удалено отсоединение от родителя?
- [ ] De-duplication принадлежащих контейнеру экземпляров больше не сохраняет
      LIFO-порядок первого создания?
- [ ] Изменён LIFO-порядок disposal?
- [ ] Порядок проверки async-disposer изменён с `Symbol.asyncDispose` на
      `Symbol.dispose`, затем `.dispose()`?
- [ ] Закешированные Promise async-фабрик больше не ожидаются перед проверкой или
      общий разрешённый ресурс может быть disposed дважды?
- [ ] Параллельные вызовы async `dispose()` перестали совместно использовать один
      Promise завершения?
- [ ] Несколько ошибок teardown больше не превращаются в `AggregateError`?
- [ ] Sync-teardown больше не сообщает об ошибочном использовании async-ресурса?

### Лазейки и динамическое использование

- [ ] Ослаблена локальная cache timing guard в `.override()` или скрыты её
      документированные ограничения для transient и принадлежащих предку
      resolutions?
- [ ] `.override()` перестал сохранять `kind`, `lazy` или `async`, стал
      нелокальным или доступным для объявленных ключей scope inputs?
- [ ] `.has()` превратился в resolver или начал менять кеши?
- [ ] `.has()` начал заявлять о готовности или безопасности синхронного
      разрешения?
- [ ] Fast-дерево стало изменяемым после активации или ослаблен контракт disposal
      «сначала потомки, затем предки»?
- [ ] Ключи, созданные во время выполнения, продвигаются как основной API?
- [ ] В core добавлены auto-wire, auto-inject, инъекция по именам параметров,
      сканирование файловой системы или discovery модулей?

## 5. Осознанные компромиссы

Документируйте эти решения, а не «исправляйте» их.

| Компромисс | Причина |
|---|---|
| Нет target ES5 или старее ES2022 | `Map`, `Symbol`, `WeakRef`, `Reflect.construct`, `Symbol.dispose` и `Symbol.asyncDispose` являются фундаментом. Пакет полифилит только disposal symbols для runtime, где их нет. Node 16+ остаётся нижней границей. |
| Нет API декораторов | DI на декораторах — другая библиотека. |
| Нет runtime-метаданных | Сигнатуры конструкторов и явные кортежи `deps` задают граф. Runtime-интроспекция добавила бы зависимости и менее надёжные режимы отказа. |
| Нет номинального различия для одинаковых структурных зависимостей | TypeScript использует структурную совместимость. Если два ключа предоставляют одинаковую форму, `DepsOf` не может знать семантическое намерение пользователя. Когда порядок сервисов одной формы важен, используйте брендированные типы или ключи `unique symbol`. |
| Нет async `get()` | `get()` остаётся синхронным. `getAsync()` оборачивает тот же синхронный resolver и возвращает Promise, не создавая отдельный registry, кеш или путь разрешения. |
| Возвращающий Promise `registerFactory` остаётся синхронным состоянием графа | Существующие фабрики могут намеренно предоставлять Promise как значение сервиса. Только `registerAsyncFactory` создаёт `AsyncSpec` и декларативное async propagation. |
| Нет обнаружения динамических циклов после Promise-границы | Декларативные async-рёбра проходят синхронный preflight и используют существующую защиту от циклов. Вызовы из legacy-фабрик с Promise-значением или захваченных контейнеров после `await` происходят после очистки resolve-stack. Разорвите такой цикл или вынесите общую инициализацию. |
| Нет runtime-обнаружения нарушений lifetime после async-границы | `AllowedDeps` по-прежнему блокирует неверные типизированные фабрики, но `as`-касты и захваченные внешние контейнеры, использованные после `await`, выполняются после очистки `singletonStack`. Полная defense-in-depth потребовала бы async-context tracking. Читайте зависимости в синхронной прелюдии фабрики. |
| Нет автоматического разрыва циклов | Циклы являются архитектурными дефектами, если только одна сторона не является явным lazy singleton companion. InferDI обнаруживает поддерживаемые runtime-циклы и сообщает о них, но не создаёт proxy или частичные экземпляры. |
| Нет обобщённых модулей `<T>(c: Container<T>) => ...` | Внутри generic-тела `keyof T` схлопывается до верхней границы `DependenciesMap`. Используйте inline-lambda в `.use()` или `Module<TRequirements, TProvides>` с объявленными требованиями. |
| Нет неявного источника scope inputs | `declareScopeInputs()` существует только в типах. Приложения явно передают принадлежащие им значения в `createScope(inputs)`; core не читает ambient request context или `AsyncLocalStorage`. |
| Нет API динамического DI-resolver | `.has(key)` — разрешённая проверка регистрации. Он не доказывает готовность или sync-режим; для статических готовых ключей вызывайте `.get()` или `.getAsync()` напрямую. |
| Нет production-сценария override | `.override()` существует для тестов и hot-reload fixtures, а его timing-проверка видит только локальный кеш. Выбор production-графа должен происходить в `.use()` или обычном builder-коде. |
| Fast mode — fixed-graph contract | `{fast: true}` получает более плоский lookup и зеркалирование singleton, доверяя инвариантам topology, lifecycle, cycle и lifetime. Стандартным остаётся checked mutable contract. |
| Нет каскадного disposal от родителя к потомку | Каждый контейнер владеет своими экземплярами. Каскадный disposal сделал бы `dispose()` нелокальным побочным эффектом и нарушил бы владение scope. |
| Нет hooks, interceptors или middleware на resolve | Это AOP. Они добавили бы работу в горячий путь и размыли контракт core. |
| Нет framework glue в core | Framework adapters находятся в пакетах адаптеров. Core остаётся независимым от зависимостей и фреймворков. |
| Нет движка анализа графа в core | Репозиторные заметки о возможном `@inferdi/graph` — предложения, а не текущий API. Любой будущий dev/CI companion должен оставаться вне production-resolution и не менять горячую форму регистрации. |

## 6. Не-цели

InferDI не станет:

- Универсальным IoC-фреймворком.
- Контейнером на декораторах или рефлексии.
- Системой request context или заменой `AsyncLocalStorage`.
- Сканером автоматического связывания.
- DSL определения providers или системой runtime-discovery модулей.
- Движком анализа графа, правил, отчётности или snapshots в production-core.
- Хостом плагинов для resolve-time middleware.
- Слоем совместимости с устаревшими DI-контейнерами.

Итоговое правило: граф — это тип, а тип — это контракт.
